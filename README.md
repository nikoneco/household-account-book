# 家計簿

主に妻が日々の入力・編集を行い、夫も入力・編集できるスマホ向け家計簿PWA。[公開家計簿](https://nikoneco.github.io/household-account-book/) はGoogleログインで利用します。GASと専用シートを接続済みです。家計情報とレシートは非公開です。

## 起動と確認

Node.js 22以上。フロントエンドの外部パッケージは不要です。

```powershell
npm test
npm run check
npm run build
npm start
```

`http://127.0.0.1:4283` を開き、「サンプルで試す」で操作を確認します。デモの入力はその画面のメモリ内だけに置き、クラウドへ保存しません。再読込で消えます。デモは実アカウントの認証検証を代替しません。

## 家計簿の計算

- 日本円の整数、日本時間、毎月1日から末日。分類は食費・酒・趣味・外食・必要経費・その他。
- 現金・銀行の購入は利用月、カードは27日締め・翌月28日請求。27日までなら利用月の翌月、28日からなら翌々月へ計上します。利用日と計上月を別々に保存し、実請求に合わせて計上月を修正できます。
- 固定費の支払実績も購入明細の1件です。固定費の予定やカードの確定請求額を支出へ加算しません。確定請求額は明細との照合に使い、差額は確認対象として表示します。
- 今月の残り＝給与－給与からの購入・支払い－今月の積立入金。購入にひも付けた取り崩し実績の分は、購入の計上月の給与支出から除外します。購入にひも付かない取り崩しは収入に足しません。予定だけでは支出にせず、残りは翌月へ持ち越しません。銀行口座残高ではありません。
- 積立は今月の予定・入金・取り崩し・残金を表示。給与30万円、開始積立50万円で50万円の購入と同額の取り崩しをひも付けた場合、今月の残りは30万円、積立残金は0円。さらに今月2万円を積立に入れた場合、残りは28万円、積立残金は2万円。取り崩し未登録の購入は給与支出に含め、ホームで未登録額を知らせます。
- 月の余り金の翌月持ち越しはありません。目的別積立残高だけは開始残高＋入金実績－取り崩し実績として累積します。
- 積立から賄う購入では、購入を1回記録し、取り崩しを資金移動としてリンクします。カードの場合は購入時に積立項目を指定し、請求月に支払いを確認して取り崩し実績を登録します。指定だけでは積立残高を減らしません。未来の日付で実績を作りません。
- 毎月の設定から月別計画を作成した後は、設定変更でその計画を更新しません。その月だけ予定額を0円にするなど、月別計画を明示的に修正できます。予定は支払実績ではありません。

## 非公開データとログイン

静的PWAとGASの匿名通信ブリッジを分離し、GASがGoogleの認証コードを直接交換します。交換先から直接受け取ったID tokenの発行者・対象OAuth client・期限・許可アカウントを確認し、短期のアプリ専用セッションを発行します。ブラウザから渡されたJWTをそのまま信頼するAPIは設けません。

Googleログインは [GISの認証コード方式](https://developers.google.com/identity/oauth2/web/guides/use-code-model) と [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) を基にしています。GAS通信は [HtmlService / google.script.run](https://developers.google.com/apps-script/guides/html/communication) の小さなiframeブリッジを通します。iframeの内側の送信元、origin、ランダムchannel、request IDを固定・照合します。公開Chromeで実ログイン・明細保存・編集・削除・非公開画像保存と表示を確認済みです。

`HOUSEHOLD_ALLOWED_EMAIL` にカンマ区切りで登録された家族は同じ家計簿を入力・編集できます。匿名と許可外アカウントの読み書きを拒否します。任意の閲覧専用アカウントは別プロパティに設定できます。公開するコードには実データ・対象シートやフォルダのID・メールアドレス・OAuth secretを含めません。ログイン情報と家計データはブラウザメモリだけに置き、Service Workerはアプリシェルだけを保存します。

## 接続設定と更新手順

初回の公開と接続設定は実施済みです。以下は再構成時の手順です。既存の設定を推測で置換せず、対象とバックアップを確認します。

1. Google CloudでWebアプリ用OAuth clientを作り、GISを呼ぶPWAのoriginを「承認済みJavaScript生成元」へ登録します。GitHub Pagesではoriginは `https://ユーザー名.github.io` で、リポジトリのパスを含めません。必要なscopeは `openid email profile` だけです。テスト公開中なら許可ユーザーも設定します。
2. GASの「プロジェクトの設定 → スクリプト プロパティ」で次の値を入れます。

| プロパティ | 内容 |
| --- | --- |
| `HOUSEHOLD_SPREADSHEET_ID` | 確認済みの非公開家計簿シート |
| `HOUSEHOLD_RECEIPT_FOLDER_ID` | 非公開レシート保存フォルダ（既存Poolを候補にする） |
| `HOUSEHOLD_ALLOWED_EMAIL` | 編集できるGoogleメールアドレス。複数なら `メール1, メール2, メール3` のようにカンマ区切り。前後の空白は除去 |
| `HOUSEHOLD_ALLOWED_EMAIL_1` など | 任意。連番で1件ずつ入れる形式にも対応。同じ許可リストにまとめる |
| `HOUSEHOLD_VIEWER_EMAILS` | 任意。閲覧専用の許可メール。複数ならカンマ区切り |
| `HOUSEHOLD_ALLOWED_SUB` | 任意。メール許可がない場合の安定したGoogleアカウントIDによる許可 |
| `HOUSEHOLD_OAUTH_CLIENT_ID` | Webアプリ用OAuth client ID |
| `HOUSEHOLD_OAUTH_CLIENT_SECRET` | 同じclientのsecret。GASだけに保存 |
| `HOUSEHOLD_PWA_ORIGIN` | PWAのorigin。パスなし。末尾スラッシュなし |

3. 本番変更前にバックアップを取り、専用シート初期化をGASエディタから行います。既存のシート1や他のシートは削除・置換しません。初期化とRPCの補助関数は末尾 `_` の内部関数として扱います。
4. GASコードの反映と、所有者として実行するWebアプリのデプロイを個別に行います。入口のブリッジは匿名で表示可能でも、家計データの操作は必ずサーバー認証を通します。
5. ignoredな `.local/runtime-config.json` に以下を置き、ビルドします。client IDとWebアプリURLはフロントの通信に必要な公開設定です。secretや家族のメールアドレスは絶対に置きません。

```json
{"mode":"google","clientId":"YOUR_CLIENT_ID.apps.googleusercontent.com","bridgeUrl":"https://script.google.com/macros/s/YOUR_DEPLOYMENT_ID/exec"}
```

6. 許可した家族それぞれの編集、第三者・匿名の拒否、ログアウト、公開PWAのiframe通信、非公開レシート画像を確認します。iPhone Safariとホーム画面からの起動は実機で確認します。

`npm run build` は静的ファイルを `dist/`、GAS用コードを `.local/gas-build/` に出力するだけです。GitHub push、clasp push、デプロイ、Sheets初期化、スケジュール作成は実行しません。ignoredな `.clasp.json` のrootDirは `.local/gas-build/` を指します。反映前に対象とrootDirを確認します。

更新はローカル検証・独立レビュー、GASのpushと既存デプロイ更新、生成したdistのgh-pagesブランチへのpush、Pagesのビルド成功、公開アセットの一致と実画面確認をそれぞれ行います。mainはソース保管用です。初期化は毎回行いません。

短時間の家計簿セッションだけを端末へ保存し、再読込・開き直しではサーバーで権限と期限を確認して復元します。有効期間はログインから最大1時間で、サーバーキャッシュの失効時も再ログインが必要です。Googleのトークンや家計記録は保存しません。ログアウトすると保存を消去し、他のタブもログアウトします。

Google認証後の準備・コード交換・記録取得中は「読み込み中」を表示します。失敗時は理由とログインボタンへ戻ります。ローカルの段階別確認は `tests/login-ui.mjs` で行います。

## レシート

「カメラで撮る」で背面カメラを呼び出し、撮影を繰り返して追加できます。「写真を選ぶ」は複数選択に対応します。まとめて保存すると写真を1枚ずつ送信し、写真別の状態と処理済み枚数のバーを表示します。失敗した写真だけ、同じ操作番号で再送できます。選択と再送情報は画面のメモリに保持し、再読み込み・ログアウトで消去します。

画像は認証後にGAS所有者の権限で非公開Driveへ保存し、SHA-256で重複を確認します。家族へのDriveフォルダ共有は不要です。JPEG/PNG/WebPの1枚8MB以下が対象です。HEIC等はJPEGなどへ変換してから登録します。カメラの起動方法や複数選択の操作は端末・ブラウザによって異なります。

履歴はレシート1枚を購入日・店名・合計の1件にまとめ、開くと商品ごとの分類・数量・金額を表示します。金額は数量分の合計です。数量が不明なら補完しません。商品の編集、削除、元画像の確認に対応します。各商品の計上月を変更した場合、履歴は表示月の分だけを合計し、詳細には購入全体を表示します。交通系マネーの購入は現金と同じ扱いです。

購入日はレシートに印字された日付です。撮影日・アップロード日・解析日で代用しません。印字された購入日は `purchaseDate`、保存日時は `uploadedAt`、各明細の利用日は `useDate` として分けます。日付・金額の欠落や合計不一致では明細を作らず要確認へ回します。混在レシートは分類ごとの行に分け、安定したlineIdを維持します。手修正や削除した明細を再解析で復元・上書きしません。

利用者のレシート画面は、画像保存と状態・元画像の確認だけです。解析結果のJSONファイルを利用者が取り込む画面は設けません。

後続の運用はChatGPTが1日1回、非公開Driveの画像を解析し、Sheetsの `HB_ReceiptInbox` へ直接結果を書き込む方式です。家計簿の明細テーブルへ直接追記せず、専用受取表へ追記します。家計簿を編集可能なアカウントで読み込むと、サーバーが最大20行ずつ検証して明細・処理状態を一括反映します。スプシへの結果保存と家計簿への反映は別の段階です。既に開いている画面は再読み込みで反映します。

取込JSONの例は [docs/receipt-example.json](docs/receipt-example.json)、スケジュール登録用の文面と列の扱いは [docs/SCHEDULE_PROMPT.md](docs/SCHEDULE_PROMPT.md) にあります。実運用版の接続先URLは非公開Driveのmdだけに記載します。ChatGPTは解析結果を受取表へ保存し、画像移動はGASが明細の取込成功後に行います。GASの任意設定 `HOUSEHOLD_RECEIPT_ARCHIVE_FOLDER_ID` で指定した非公開フォルダへ元のfileIdのまま移動し、履歴の画像表示を保ちます。移動だけ失敗した場合は次回の編集者の読込で移動だけ再試行します。通常チャットの画像読取とSheets書込はユーザー報告で成功し、移動は403で拒否されたためGASへ移しました。GASの自動移動とChatGPTの定期実行の実試験は別工程です。有料AI APIやGASの定期トリガーは導入していません。

## データ構造

専用タブは `HB_Expenses`（明細）、`HB_Settings`（毎月設定）、`HB_Plans`（固定された月別計画）、`HB_Transfers`（積立入出金）、`HB_Incomes`、`HB_Bills`（照合）、`HB_Receipts`、`HB_Operations`（再試行用IDと結果）、`HB_Meta`（スキーマ・revision）、`HB_ReceiptInbox`（外部解析結果の受取）の10表です。記録は安定したIDとJSONを保存します。JSONは文字列として保存するため、ユーザー入力をSheets数式として実行しません。

複数テーブルの保存はGASのscript lockとSheetsの一括更新で処理します。変更された行だけを書き込み、同じ操作の再試行では保存を重複実行しません。再試行履歴はサーバーに保持し、画面へ送るstateからは省きます。画面が古い場合はrevision不一致を検出し、再読込を案内します。通常はアプリから修正し、外部解析は `HB_ReceiptInbox` のA:B列への追記だけを行います。

検証結果と未確認範囲は [docs/VERIFICATION.md](docs/VERIFICATION.md) に記録します。
